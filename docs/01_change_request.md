# 改修依頼書:受注CSV取込バッチ

> 受講者に配布する題材です。実務の依頼書を想定し、**意図的に曖昧な点を残しています**。
> 曖昧な点を洗い出し、確認事項として整理するところからハンズオンを始めます。

## 1. 背景

営業部門から次の問い合わせがありました。

- 「基幹システムの出力が先月から UTF-8 になった拠点があり、取り込めない」
- 「再送されたCSVを取り込むと、全部取り込まれなくなってしまう」
- 「取り込んだ件数やエラー件数が分からず、毎回ログを開いて数えている」

## 2. 依頼内容

| No | 依頼 | 備考 |
|---|---|---|
| R1 | UTF-8(BOMあり・なし)のCSVも取り込めるようにしてほしい | 従来のCP932も引き続き取り込めること |
| R2 | 同じ `order_id` が既にある場合は、新しい内容で更新してほしい | 再送データの取込を想定 |
| R3 | 取込結果(読込件数・登録件数・更新件数・エラー件数)を画面に出してほしい | 夜間ジョブのログにも残したい |
| R4 | エラー行があった場合は、運用側で気づけるようにしてほしい | 方法は任せる |

## 3. 制約・前提

- 既存のテストは引き続き成功すること(仕様変更に伴う修正は理由を説明できること)
- 外部ライブラリは追加しない(`pom.xml` に新しい依存を追加しない)
- `scripts/run_nightly.sh` は運用部門の管理物のため、**原則として変更しない**
- `Report.java`(月次集計)の出力結果は変わらないこと

## 4. 曖昧な点(例:講師用。受講者には配布しない)

受講者が確認事項として挙げられるとよい点です。

- R1:文字コードは「自動判定」か「引数で指定」か。判定に失敗したらどうするか
- R2:ファイル内に同じ `order_id` が複数ある場合はどちらを採用するか(先勝ち/後勝ち/エラー)
- R2:更新した行は「登録件数」と「更新件数」のどちらに数えるか
- R3:「画面に出す」は標準出力でよいか。ログファイルとの関係は
- R4:「気づけるように」は終了コードか、通知か、ログか。**終了コードを変えると `run_nightly.sh` の動き(`set -e`)が変わる**
- 全般:エラー行があった場合も、正常行は登録を続けるのか(現行どおりか)
- 全般:取込は1ファイル単位でトランザクションを張るべきか(途中で落ちたときの扱い)
