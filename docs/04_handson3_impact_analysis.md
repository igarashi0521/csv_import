# ハンズオン③:既存ソース解析・変更影響(30分)

**ねらい**:AIに既存ソースを読ませて構造と影響範囲を把握し、**AIの説明が正しいかを自分で確認する**体験をする。

## 進め方

| 時間 | 内容 |
|---|---|
| 2:40-2:50 | AIにソース構造を説明させ、処理の流れ図を作らせる |
| 2:50-3:05 | 「R4(終了コードの変更)」の影響範囲をAIに洗い出させる |
| 3:05-3:10 | 影響範囲を人が確認し、判断記録を書く |

## Step 1:ソース構造の把握

AIに次を依頼します。

- `src/main/java/com/example/csvimport/` の各ファイルの責務
- `Batch.java` の処理の流れ(入力から DB登録まで)
- 呼び出し関係(どの関数がどこから使われているか)

**確認すること**

- [ ] AIの説明を、実際のコードと照らして確認したか(特に関数の呼び出し元)
- [ ] 説明に、コードに存在しない関数・ファイルが含まれていないか

## Step 2:変更影響の洗い出し

次の2つの変更について、影響を受ける箇所をAIに挙げさせます。

**変更A**:`Batch.run()` の終了コードを「エラー行があれば 2」に変える(R4)

**変更B**:DBの `order_date` の保存形式を `YYYY-MM-DD` から `YYYYMMDD` に変える(仮の変更)

| 変更 | AIが挙げた影響箇所 | 人が確認した結果(正しい/漏れ/誤り) |
|---|---|---|
| A | | |
| B | | |

**ヒント(確認用)**

- 変更Aは、`scripts/run_nightly.sh` が `set -e` で動いている点に注意
- 変更Bは、`Repository.insertOrder()` の保存時(`toString()`)と、`Repository.fetchOrdersByMonth()` の `LIKE` 条件・`LocalDate.parse()` に注意(`Report.java` は `Repository` 経由で日付を受け取る)
- 影響範囲の確認には、`grep` による呼び出し元の検索が有効

## 補足

実務では、運用側スクリプトや他システムなど**ソース外の依存**はAIには見えません。
「AIが見つけられなかった影響」が無いか、依頼者・運用担当に確認する姿勢が重要です。
