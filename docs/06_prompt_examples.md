# 「指示・比較・検証」プロンプト例

AIへの丸投げではなく、**指示 → 比較 → 検証** のサイクルで使うことを重視します。
以下は例です。そのまま使うのではなく、自分の言葉に直して使ってください。

## 1. 指示(目的・範囲・制約・完了条件を伝える)

### 悪い例

```
CSV取込バッチを改修して
```

### 良い例

```
受注CSV取込バッチ(src/main/java/com/example/csvimport/)を改修します。
目的:同じ order_id が既にDBにある場合、エラーにせず新しい内容で更新したい。
対象:Repository.java と Batch.java のみ。CsvParser.java と Validator.java は変更しない。
制約:pom.xml に依存を追加しない。既存テストは壊さない。Report.java の出力は変えない。
完了条件:orders_ok.csv を2回取り込んでもエラーにならず、2回目は「更新」として数えられる。
まず変更方針を説明し、私が了承してから実装してください。
```

## 2. 比較(選択肢と判断材料を出させる)

```
重複 order_id の扱いについて、実装方針を3案出してください。
それぞれについて、変更範囲・リスク・テストのしやすさ・運用への影響を
表で比較してください。最後に、あなたの推奨案と理由も示してください。
ただし最終判断は私がします。
```

```
案Bの「INSERT OR REPLACE」と「ON CONFLICT DO UPDATE」の挙動の違いを、
SQLiteのバージョン要件も含めて説明してください。
確信が持てない点は、そう明記してください。
```

## 3. 検証(出力を疑い、確かめる)

```
今の変更で、次のケースは正しく動きますか?コードを根拠に説明してください。
- ファイル内に同じ order_id が2行ある
- 空のCSV
- UTF-8 BOM付きで、先頭の列名が order_id と一致しないケース
```

```
追加したテストについて、「このテストが通っても検出できないバグ」を挙げてください。
```

```
この変更で影響を受ける箇所を、リポジトリ内の呼び出し元を検索して洗い出してください。
推測ではなく、実際にコードを検索した結果に基づいてください。
```

```
あなたの説明のうち、実際にコードを実行して確認していない部分はどこですか?
```

## 4. 差分レビュー

```
次の差分をレビューしてください。観点は「バグ」「エッジケース」「可読性」
「要件との整合」です。指摘は重要度順に、該当箇所を示してください。
```

## 使い方のポイント

| ポイント | 理由 |
|---|---|
| 先に自分で考えてからAIに聞く | AIの出力を評価できるようになる |
| 小さく頼み、都度確認する | 間違いに早く気づける |
| 根拠(コード・実行結果)を求める | 推測と事実を区別できる |
| 最終判断は人がする | 責任の所在を明確にする |
| 機密情報・個人情報を入力しない | 社内ルールに従う(題材は架空データ) |
