# 差分レビュー観点

AIが生成した変更は、**人が差分を読んで承認する**ところまでが作業です。
ハンズオン③の後(または、ハンズオン②の最後)に、自分の変更の差分をレビューします。

```sh
git diff            # 変更の確認(git管理している場合)
```

## 1. 要件との整合

- [ ] R1〜R4 のすべてに対応しているか(対応漏れ・過剰対応がないか)
- [ ] 要件整理で決めた方針どおりの実装か
- [ ] 依頼書の制約(`pom.xml` に依存を追加しない、`run_nightly.sh` 不変、`Report.java` の出力不変)を守っているか

## 2. バグ・エッジケース

- [ ] 空ファイル、ヘッダーのみ、1行のみのCSVで動くか
- [ ] 文字コード判定が誤るケース(CP932でUTF-8として読める文字列、判定失敗時)
- [ ] 重複 `order_id`(DB既存/ファイル内)の扱いが決めた仕様どおりか
- [ ] 途中でエラーが起きたとき、DBが中途半端な状態にならないか(コミット位置・ロールバック)
- [ ] 件数(読込=登録+更新+エラー)の整合が取れているか
- [ ] 接続やファイルが、例外時にも閉じられるか
- [ ] (Java)`Connection` / `PreparedStatement` / `ResultSet` が try-with-resources で閉じられているか。`autoCommit` の扱いが意図どおりか

## 3. 可読性・保守性

- [ ] 関数の責務が1つに保たれているか(`run()` が肥大化していないか)
- [ ] 命名が既存コードの流儀と合っているか
- [ ] 不要な変更(無関係なリファクタリング、整形のみの差分)が混ざっていないか
- [ ] コメントは「なぜ」を説明しているか(コードの言い換えになっていないか)

## 4. テスト

- [ ] 新しい挙動ごとにテストがあるか
- [ ] 既存テストを書き換えている場合、その理由を説明できるか
- [ ] テストが実装の写しになっていないか

## 5. 人が最終確認する項目(AIに任せない)

- [ ] 仕様判断(重複時の扱い、終了コードの意味)は、決めた人が説明できるか
- [ ] 運用への影響(夜間ジョブ、既存の利用者)を確認したか
- [ ] 「AIが言っていること」を、実際に実行して確かめたか

## レビューコメントの書き方(例)

```
[指摘] Batch.java:45  ファイル内で order_id が重複した場合の件数が「更新」に二重計上されます。
       要件整理で「後勝ち、更新件数に1回だけ数える」と決めたため、仕様と異なります。
[確認] Repository.java:30  INSERT OR REPLACE を使っていますが、将来カラムが増えた場合に
       既存値が消える点は許容でしょうか。
[軽微] CsvParser.java:12  変数名 `enc` は `charset` の方が既存コードと揃います。
```
